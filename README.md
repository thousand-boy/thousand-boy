## ポートフォリオ

### 01. 書類確認漏れ防止Webアプリ

| 状況 | 予定技術 |
| --- | --- |
| 要件整理・設計中 | Java / Spring Boot / PostgreSQL / JUnit |

医療現場で経験した書類確認漏れの問題をもとに、**「誰が・何を・どこまで確認したか」をシステム上で管理する**Webアプリを制作しています。

Java / Spring Bootを使ったバックエンド開発を学ぶためのポートフォリオでもあります。

#### 背景

以前の職場では、書類の確認漏れが月30件前後発生していました。

発生内容を分析すると、主に次の問題がありました。

- 漏れが特定の書類に集中している
- 確認担当者が明確になっていない
- 複数人で確認するため、役割分担があいまいになっている

そこで確認担当者と確認手順を整理し、**確認漏れを月7〜8件程度まで減らしました。**

> この改善はWebアプリ導入によるものではなく、Webアプリを作る前に行った業務改善による結果です。

この経験をもとに、人の注意だけに頼らず確認状況を管理できる仕組みとしてWebアプリを設計しています。

#### 予定している機能

- 書類の登録・編集・削除（CRUD）
- 確認担当者の管理
- 確認ステータスの更新
- 未確認書類の一覧表示
- 変更履歴の保存

実装では、REST API、PostgreSQLへのデータ保存、入力値のバリデーション、例外処理、JUnitによる単体テストに取り組む予定です。

#### 開発の進め方

**課題整理 → 要件整理 → 設計 → 実装 → テスト → 改善**

という流れを意識して開発し、設計した理由や発生した問題、その調査・修正内容をREADMEやGitの履歴に残していきます。

> 患者情報や職員の個人情報は使用せず、すべて架空または匿名化したデータで開発します。

### [02. 勤務表作成支援ツール](https://github.com/thousand-boy/kinmu-automation)

| 状況 | 使用技術 | リポジトリ |
| --- | --- | --- |
| 試作品（動作検証中） | Python / OR-Tools / openpyxl / pytest / GitHub Actions | [kinmu-automation](https://github.com/thousand-boy/kinmu-automation) |

Excelに入力した職員情報と勤務希望をもとに、**Pythonと数理最適化（OR-Tools）を使って勤務表の下書きを作成するツール**です。

出力をそのまま確定するのではなく、担当者が内容を確認・調整してから使用することを前提としています。

#### 背景

勤務表では、休日数や勤務希望、病棟ごとの人数、職種・役割の配置、連続勤務など、多くの条件を同時に考える必要があります。

そこで勤務ルールを、

- 必ず守る条件
- できるだけ満たしたい条件
- 人が最終的に判断する内容

に分け、プログラムで扱える条件をOR-Toolsの制約として設定しています。

#### 実装している内容

- **読み込み**：Excel勤務表と職員マスタから、病棟・役割・在籍状況・勤務希望・必要休日数などを取得
- **最適化**：OR-Tools（CP-SAT）で勤務パターンを探索。通常モードで解が得られない場合は4連勤の条件だけを緩和し、条件の両立不能と時間切れを区別して扱う
- **出力**：勤務結果をExcelへ書き込み、追加した職員行には必要な書式・数式などを引き継ぐ。一時保存したファイルを再読み込み・検証し、問題がない場合のみ正式な出力へ置き換える
- **テスト**：pytestによる個別機能・最適化・保存処理・統合テストを実施し、GitHub Actionsでもpush / pull request時に自動実行

#### 制約条件の例

```text
【必ず守る】
・勤務と理由を入力した予定は変更しない
・在籍職員全員に必要休日数をちょうど割り当てる
・日曜日は各病棟ちょうど2名が出勤する

【通常は守る】
・自動配置による4連勤は禁止する
  → 通常モードで解が得られない場合のみ緩和し、
    4連勤を減らすことを最優先にする

【できるだけ満たす】
・月〜土は各病棟に専従または専任を1名以上配置する
・月〜土は全体で作業療法士を1名以上、可能なら2名配置する
・水〜金は各病棟の休みを2名以内に近づける
・「休→出→休」のような細切れの勤務を減らす
```

#### このプロジェクトで取り組んでいること

このプロジェクトでは、**実際の業務ルールを整理し、プログラムが扱える制約条件へ変換すること**と、プログラムに任せる範囲と人が確認する範囲を分けることに取り組んでいます。

機能が増えて1つの `main.py` では修正箇所を追いにくくなったため、読み込み・検証・最適化・出力などの役割ごとにモジュールを分割しました。

リファクタリング時には、変更前後で制約や評価ロジックが変わっていないこともテストで確認しています。
